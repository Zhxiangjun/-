## 2 建设背景与架构挑战

### 2.1 建设背景

齐河职专为山东省齐河县职业中等专业学校，属中等规模中等职业学校，在校生 3000—6000 人，拥有 1—2 个校区。学校现有信息化系统以"烟囱式"建设为主：视频监控、门禁、一卡通、教务、宿管、能耗等各自独立，数据不互通、事件不联动、管理靠人工，存在以下典型痛点：

1. **数据孤岛**：人员信息在教务、学籍、门禁、一卡通中多份维护，口径不一致，转专业、休学、毕业等异动无法自动同步。
2. **事件被动**：安防以"事后查录像"为主，缺少实时预警与自动派单，值班人员靠人盯屏，夜间盲区多。
3. **联动缺失**：请假、离校放行、查寝、考勤之间无自动闭环，依赖班主任手工核对。
4. **扩展困难**：新增设备需重新对接，缺少统一 IoT 接入与规则引擎，二次开发成本高。
5. **成本敏感**：作为中职学校，预算有限，不能照搬高校"重硬件、重集成"的大投入模式。

### 2.2 由此产生的架构挑战

| 序号 | 挑战 | 架构应对策略 |
| --- | --- | --- |
| C1 | 硬件预算有限，无法部署大规模 GPU 集群 | 采用"边缘抽帧 + 轻量模型 + 事件上云"策略，单卡承载多路分析；中心侧只处理事件与结构化数据 |
| C2 | 网络条件不稳定，闸机断网即瘫痪 | 边缘/终端侧本地白名单与本地决策，断网续传，业务不中断 |
| C3 | 开发团队以师生为主，技术栈需收敛 | 统一 Python（FastAPI）+ Vue3 + PostgreSQL 主线，减少异构组件；容器化交付降低环境成本 |
| C4 | 生物特征数据合规要求高 | 人脸特征向量加密存储、原始图最小化留存、告知—同意—撤回全流程在线化 |
| C5 | 未来要产品化对外销售 | 多租户化预留、配置化交付、标准化硬件适配层、许可授权机制前置设计 |
| C6 | 需同时满足竞赛演示与真实生产 | 竞赛版与商业版双轨选型（见第 7 章），同一代码基线通过配置切换 |

## 3 架构设计目标与原则

### 3.1 架构设计目标

| 目标维度 | 量化目标 | 验证方式 |
| --- | --- | --- |
| 业务覆盖 | 100% 覆盖 12 个一级模块、不少于 60 个二级功能点 | 需求追溯矩阵逐条核对 |
| AI 能力 | 支持不少于 10 类视觉算法；边缘 1080p 单路分析 ≥15 FPS，告警端到端时延 ≤500 ms（本地） | 现场压测 + 算法评测报告 |
| 并发能力 | 支持 6000 注册用户、1500 并发在线、门禁鉴权 ≥30 TPS | 压力测试报告 |
| 响应性能 | 门禁鉴权 P95 ≤300 ms；列表查询 P95 ≤800 ms；大屏首屏 ≤3 s | APM 与压测数据 |
| 可用性 | 核心服务年可用性 ≥99.9%（年不可用 ≤8.76 h）；门禁离线可用率 100% | 监控统计 + 演练 |
| 数据能力 | 主数据唯一可信；ODS→ADS 数据链路 T+1 与准实时（≤5 min）双通道 | 数据质量报告 |
| 安全合规 | 满足等保 2.0 三级要求；人脸等生物特征处理合规留痕 | 等保测评 + 合规自查表 |
| 成本控制 | 单校区最小可行配置硬件投入可控在 15 万元以内；推荐配置 ≤60 万元 | 采购清单核算 |
| 可产品化 | 平台核心与校方定制解耦，行业模板化交付，新校上线 ≤2 周 | 交付演练 |

### 3.2 架构设计原则

1. **先进性**：采用云原生、微服务化、边缘智能、事件驱动等技术路线，AI 能力以"模型即服务"方式沉淀，避免算法与业务代码耦合。
2. **可靠性**：核心链路无单点，关键服务双实例；终端侧具备离线自治能力；故障时优先保通行、保安全、保数据不丢。
3. **安全性**：默认拒绝、最小权限、纵深防御；身份、数据、设备三线并重；安全能力内建于平台层而非事后叠加。
4. **可扩展**：横向扩展优先（无状态服务 + 队列削峰 + 分区表）；设备接入采用驱动插件化，新增品类不改主流程。
5. **低成本可落地**：能复用不新建，能边缘不中心，能开源不商业；用软件能力替代硬件堆砌；分档配置，按需演进。
6. **国产化适配**：操作系统、数据库、中间件、芯片可选国产替代路径（麒麟/统信、openGauss/达梦、鲲鹏/飞腾/昇腾），应用层不绑定特定底层。
7. **标准先行**：优先采用 GB/T 28181、ONVIF、RTSP、Wiegand、Modbus、MQTT 等标准协议，私有协议一律封装为驱动，避免被单一厂商锁定。
8. **数据驱动**：一次采集、多方复用；主数据统一管理，指标口径统一定义，禁止跨模块直连对方业务库。
9. **可运维**：全链路可观测（日志、指标、链路、告警），配置化发布，灰度与回滚能力内建。
10. **合规为本**：个人信息最小必要收集，生物特征"本地优先、加密存储、留痕可查、限期删除"。

### 4.4 关键业务联动的事件流设计

平台采用**事件驱动 + 规则引擎**实现跨模块联动，核心事件流如下：

**（1）门禁通行 → 教职工考勤**

```
闸机/一体机刷脸 → 边缘识别(≤300ms) → 生成通行事件 access.passed
   → MQTT 上报平台 → IoT 网关校验 → 规则引擎匹配"考勤规则"
   → 写入 biz_attendance（上班/下班判定，含多校区/多点取最早最晚）
   → 异常（迟到/缺卡）→ 通知中心推送本人 + 人事管理员 → 生成补卡工单
```

**（2）学生请假 → 离校放行 → 归寝核对**

```
学生小程序提交请假 → 工作流(班主任→学工→宿管)审批 → 审批通过事件 leave.approved
   → 规则引擎下发"临时通行授权"至边缘网关（白名单增量同步，含有效期）
   → 闸机放行 → access.passed(student, gate) → 标记"已离校"
   → 宿舍查寝任务(定时) → 核对该生应到/实到 → 未归且无有效请假 → 预警事件
   → 值班人员派单处置 → 处置结果回写事件
```

**（3）访客预约 → 临时权限 → 车辆放行**

```
访客线上预约(被访人确认) → 生成 visitor.pass（二维码+人脸可选）→ 下发闸机/道闸
   → 到访刷码/刷脸 → 人行闸机放行 → 车牌识别匹配预约车牌 → 车行道闸放行
   → 全程留痕：到访时间、轨迹点、被访人、离场时间 → 超时未离场 → 提醒被访人
   → 住宿登记需求：按当地公安要求上报（如需）
```

**（4）AI 预警 → 自动派单**

```
视频流 → 边缘 AI 推理 → 命中算法(如周界入侵) → 多帧确认(N 帧 M 命中)
   → 区域过滤(电子围栏) → 时间窗抑制(去重) → 生成 ai.alert 事件(含截图/短视频)
   → 平台接收 → 规则引擎按"点位-时段-级别"匹配派单策略 → 生成工单
   → 通知中心推送值班人(App/短信/语音) → 值班人接单处置 → 处置留痕 → 事件闭环
   → 误报标记回流 → 模型迭代数据集
```

## 5 逻辑架构与部署架构

### 5.1 逻辑架构

逻辑上平台分为**四横两纵**：接入域、能力域、业务域、数据域，以及安全域与运维域。

| 逻辑域 | 组成 | 设计要点 |
| --- | --- | --- |
| 接入域 | API 网关（Nginx/APISIX）、IoT 网关（EMQX）、视频接入（GB28181/ONVIF/RTSP）、Webhook 出口 | 统一入口，限流、鉴权、审计前置；设备与用户双通道 |
| 能力域 | IAM、工作流、规则引擎、通知中心、文件服务、AI 推理调度、模型管理、任务调度 | 能力服务化，被业务模块复用；无状态可横向扩展 |
| 业务域 | 12 个一级模块对应的业务微服务（可按"人员通行域/安防域/生活域/教学域/能源域/分析域"聚合部署） | 按领域拆分，避免过度微服务化；竞赛版可合并为单体多模块 |
| 数据域 | PostgreSQL（事务）、TDengine（时序）、Redis（缓存/会话）、MinIO（对象）、可选向量库 | 一数一源，读写分离，冷热分层 |
| 安全域 | 身份、权限、加密、脱敏、审计、合规留痕 | 贯穿接入/能力/业务/数据 |
| 运维域 | 监控、日志、链路、配置、发布、备份、演练 | 全链路可观测 |

**单校区部署要点**

1. 服务器区、视频专网、门禁物联网区三层 VLAN 隔离，跨区访问仅放通必要端口（应用→视频平台 554/5060、应用→IoT 1883/8883）。
2. 门禁与道闸控制器、边缘网关部署在门卫室/弱电间，具备断网本地决策能力。
3. NVR 就近存储视频，平台仅拉取事件片段与结构化数据，降低骨干带宽压力。
4. 数据库主备（流复制 + 定时全备），备份介质异机存放，重大变更前手工快照。

### 5.3 双校区级联方案

采用**"主中心 + 分中心"级联**模式，避免跨校区强耦合：

```
    【主校区(A)】                                【分校区(B)】
 核心业务集群(应用/数据库/数据中台) <—— SD-WAN/VPN 专线 ——> 分中心节点(边缘+缓存库)
   |            ^                                            |
   |  同步:主数据下发 / 事件上行(异步,断网缓存)                |
   v            |                                            v
 全量视频存储    +-------- 只上传事件片段与结构化数据 ---------+ 本地 NVR 全量存储
```

| 设计项 | 方案 |
| --- | --- |
| 主数据 | 主校区为唯一主本，分校区只读缓存，增量下发（≤30 s 或变更即时推送） |
| 业务数据 | 分校区写本地库（异步复制至主中心），主中心聚合分析；冲突按"本地优先 + 时间戳仲裁" |
| 通行授权 | 白名单由主中心生成，双校区各自下发到本地边缘网关；支持"跨校区通用权限"标记 |
| 视频 | 各校区本地全量存储，跨校区仅按需调阅事件片段（RTSP 转发/GB28181 级联） |
| 链路 | 主用运营商专线（≥200 Mbps 对称）+ 备用 4G/5G；断链时本地自治，恢复后按序补传 |
| 时钟 | 双校区统一 NTP 源，偏差 ≤50 ms，保证事件时序可比 |
| 容灾 | 主中心故障时，分中心可独立运行门禁/安防核心业务不低于 72 h |

### 5.4 三种部署形态对比

| 对比项 | 私有化部署（本地机房） | 公有云部署（SaaS/专属云） | 混合部署 |
| --- | --- | --- | --- |
| 适用场景 | 数据敏感、无稳定外网、需满足等保本地测评 | 无自建机房、预算有限、需快速上线、多校统一运营 | 视频/门禁本地化、分析与备份上云 |

| 年度成本 | 低（电费+维保+人力） | 中高（云资源+带宽） | 中 |
| 数据主权 | 完全自主 | 依赖云商合规能力 | 核心数据自主，分析数据上云 |
| 扩展性 | 受本地资源限制 | 弹性好，秒级扩容 | 弹性与自主兼顾 |
| 运维复杂度 | 高（自建监控/备份/安全） | 低（云商托管） | 中 |

| 推荐度（本项目） | ★★★★★ 竞赛与首校落地 | ★★☆☆☆ 备选，适合未来多校 SaaS | ★★★☆☆ 双校区或算力不足时采用 |

### 6.2 带宽估算方法与示例

#### 6.2.1 计算方法

| 场景 | 公式 | 说明 |
| --- | --- | --- |
| 视频接入带宽 | `B_video = N × R × K` | N 路数，R 单路码率，K 协议与突发冗余系数（取 1.2） |
| 视频存储容量 | `S = N × R × 3600 × 24 × D ÷ 8 ÷ 1024` | S 单位 GB，R 单位 Mbps（换算为 MB/s 需 ÷8），D 天数；另加 RAID 开销系数 1.2 |
| AI 分析上行带宽 | `B_ai = N_ai × F × E` | N_ai 分析路数，F 事件频率（次/分钟），E 单事件字节（含截图，约 300 KB） |
| 门禁业务带宽 | `B_access = TPS × E_access` | 单次请求+响应约 2 KB |
| 物联网采集带宽 | `B_iot = P × (1/T) × E_p` | P 测点数，T 采集周期（秒），E_p 单点字节（约 100 B） |
| 中心出口带宽 | `B_wan = B_notify + B_remote + B_cloud_backup` | 短信/推送/远程调阅/异地备份 |

#### 6.2.2 示例一：单校区 200 路 1080p 视频

- 单路主码流取 3 Mbps，冗余系数 1.2。
- 接入总带宽 `B_video = 200 × 3 × 1.2 = 720 Mbps`。
- 结论：接入层千兆到楼栋（每台 24 口 PoE 交换机接入 20 路 ≈ 72 Mbps，余量充足），**核心层与视频存储需万兆上联**（720 Mbps 已接近千兆实际可用上限的 72%，叠加突发与巡检回放需万兆）。

#### 6.2.3 示例二：200 路视频存储 15 天

- `S = 200 × 3 × 3600 × 24 × 15 ÷ 8 ÷ 1024 ≈ 94,900 GB ≈ 92.7 TB`。
- 加 RAID6 与热备开销系数 1.2，裸容量需求 ≈ 111 TB。
- 选型：12 盘位 × 10 TB × 2 台（裸容量 240 TB）或 24 盘位 IPSAN 一套，剩余空间用于事件片段 90 天留存。

#### 6.2.4 示例三：AI 分析 40 路事件上行

- 高峰期每路 0.5 次告警/分钟，单事件约 300 KB（含 1 张截图 + 5 s 短视频 2 MB 时另算）。
- 仅截图：`B_ai = 40 × 0.5 × 300 KB ÷ 60 ≈ 100 KB/s ≈ 0.8 Mbps`。
- 含短视频（2 MB）：`40 × 0.5 × 2.3 MB ÷ 60 ≈ 0.77 MB/s ≈ 6.1 Mbps`。
- 结论：AI 事件上行带宽压力小，瓶颈在中心侧存储与消息处理，可用 MQTT + 异步队列削峰。

#### 6.2.5 示例四：物联网测点采集

- 2000 个测点，5 分钟采集一次，单点 100 B：`B_iot = 2000 × 100 ÷ 300 ≈ 667 B/s ≈ 5.3 kbps`。
- 结论：物联网带宽可忽略，主要成本在网关数量与施工，宜按楼栋集中接入。

#### 6.2.6 示例五：门禁鉴权并发

- 早高峰 15 分钟内 2000 人次通过 4 个门点：`TPS = 2000 ÷ 900 ≈ 2.2 次/秒`，峰值取 3 倍 ≈ 7 TPS。
- 每个门点本地鉴权（离线白名单）承担绝大部分流量，平台侧仅处理鉴权结果上报（约 7 KB/s），**中心不可用时业务不感知**。

### 6.4 设备接入统一规范

1. **三层接入模型**：设备原始协议 → 边缘网关/驱动（协议转换、鉴权、限流）→ 平台 IoT 网关（统一物模型）。
2. **统一物模型**：每类设备定义 `productKey + deviceId + 属性/事件/服务`，属性如 `online`、`doorState`、`temperature`；事件如 `access.passed`、`alert.fired`；服务如 `openDoor`、`reboot`。
3. **心跳与离线判定**：心跳周期 30 s，连续 3 次丢失判定离线并告警；离线设备的事件在恢复后 5 min 内补传。
4. **时间同步**：所有设备启用 NTP，与平台时钟偏差 >5 s 时告警。
5. **固件与配置管理**：支持批量下发配置与固件升级，升级窗口默认 02:00—05:00，失败自动回滚。

### 8.3 训练与调优流程

| 阶段 | 操作 | 关键参数 | 判据 |
| --- | --- | --- | --- |
| 基线训练 | 公开预训练权重迁移学习 | 输入 640、batch 32、epochs 200、SGD/AdamW、初始 lr 0.01 | mAP@0.5 达到基线 |
| 微调 | 加入校内场景数据，冻结骨干前 1/3 | lr 降至 0.001，余弦退火 | 场景 mAP 提升 ≥5% |
| 难例挖掘 | 对误报/漏报样本加权重训（OHEM） | 难例权重 ×2 | 误报率下降 ≥30% |
| 剪枝与量化 | 通道剪枝 20%—30% + FP16/INT8 量化 | 精度损失 ≤2% mAP | 推理速度提升 ≥1.5× |
| 蒸馏（可选） | 大模型（YOLOv8m）蒸馏到小模型（YOLOv8n） | 温度 4、α=0.7 | 小模型精度接近大模型 |
| 导出与验证 | 导出 ONNX，在目标硬件上端到端验证 | opset 17、动态 batch | 与 PyTorch 结果偏差 ≤1e-3 |
| 上线与灰度 | 新模型先在 10% 点位上灰度 7 天 | 影子模式对比 | 误报不高于旧模型 |
| 迭代 | 按"误报标记回流 → 周度重训"闭环 | 每 2 周一次 | 指标持续改善 |

### 8.4 边缘推理性能目标

| 指标 | 目标值 | 测量方法 | 不达标处理 |
| --- | --- | --- | --- |
| 单路 1080p 分析帧率 | ≥15 FPS（人员检测类）；时序类 ≥10 FPS 等效 | 边缘侧埋点统计实际推理帧率 | 降抽帧率、降分辨率、切换 INT8 |
| 单路端到端时延 | ≤500 ms（从取帧到事件生成） | 时间戳差值 P95 | 缩短队列、关闭非必要预处理 |
| 单卡并发路数 | RTX 3060 12 GB ≥8 路；RTX 4090 24 GB ≥20 路（按 3 FPS 抽帧） | 压测（同时拉流） | 增加抽帧间隔至 1—2 FPS |
| 显存占用 | 模型常驻 ≤1.5 GB/实例；每路 ≤300 MB | nvidia-smi 采样 | 共享模型实例（多路复用同一 session） |
| CPU 占用 | 单路 ≤8%（8 核） | top 采样 | 使用硬件解码（NVDEC/QSV） |
| 推理准确率 | 与中心 GPU 结果一致（偏差 ≤1% mAP） | 同一测试集对比 | 检查量化与预处理差异 |
| 连续运行稳定性 | 7×24 h 无内存泄漏，进程异常自愈 ≤30 s | 长稳测试 | 引入看门狗与自动重启 |
| 断网续传 | 本地缓存 ≥72 h 事件，恢复后 5 min 内补传完成 | 断网演练 | 扩容本地磁盘、压缩事件 |

**边缘侧处理流水线**

```
RTSP 拉流 → 硬件解码(NVDEC/QSV) → 帧抽样(3 FPS) → 预处理(缩放/归一化)
   → 模型推理(ONNX Runtime) → NMS/后处理 → 业务规则(区域/时长/越界)
   → 多帧确认 + 去重 → 事件封装(截图+元数据) → 本地缓存 + MQTT 上报
                          ↑                                            ↓
                    断网时仅缓存 ←────────── 平台 ACK 确认 ──────────┘
```

### 8.5 告警去重与误报抑制策略

| 策略 | 规则设计 | 参数建议 | 效果 |
| --- | --- | --- | --- |
| 多帧确认 | 连续 N 帧中至少 M 帧命中才产生事件 | N=10，M=6（时间类）；N=5，M=3（烟火） | 过滤瞬时误检，误报下降 60%—80% |
| 置信度阈值 | 按算法分别设定，并叠加类别阈值 | 人员 0.45；烟火 0.55；周界 0.50；通道占用 0.50 | 平衡召回与误报 |
| 区域过滤 | 电子围栏（多边形）+ 忽略区（树木、旗杆、水面、屏幕反光） | 每点位独立配置 | 消除天然干扰源 |
| 目标尺寸过滤 | 目标框高度 <40 px 不判定 | 40—60 px 按点位调整 | 过滤远处小目标误检 |
| 时间窗抑制 | 同点位同算法在 T 秒内只上报一次（合并计数） | T=60 s（周界）、300 s（通道占用） | 消息量下降 70% |
| 目标 ID 去重 | 同一跟踪 ID 在存活期内不重复告警 | 跟踪存活 3 s | 消除同目标连续告警 |
| 时段策略 | 非工作时段提高灵敏度，工作时段降低 | 22:00—06:00 阈值 -0.05 | 按场景平衡 |
| 告警风暴抑制 | 单点位 5 min 内超 10 条自动降频并提示"疑似持续事件" | 阈值可配 | 防止刷屏 |
| 人工反馈闭环 | 值班人标记误报 → 进入难例库 → 周度重训 | 误报样本自动入库 | 长期持续降误报 |
| 天气自适应 | 雨雪/大风天气启用额外过滤（形态学去噪 + 高阈值） | 接入气象接口或手工切换 | 恶劣天气误报下降 50% |

### 8.6 算法评测指标与验收标准

| 指标 | 定义 | 目标值（验收线） | 理想值 |
| --- | --- | --- | --- |
| mAP@0.5 | 平均精度均值 | 人员检测 ≥0.85；烟火 ≥0.75；安全帽 ≥0.80 | 分别 ≥0.90 / 0.82 / 0.86 |
| 召回率 Recall | 正样本命中比例 | 周界入侵 ≥95%；烟火 ≥90% | ≥97% / ≥93% |
| 准确率 Precision | 上报中真实事件比例 | ≥85%（周界）；≥80%（烟火） | ≥92% / ≥88% |
| 误报率 | 每路每天误报条数 | ≤5 条/路/天（周界）；≤2 条/路/天（烟火）；≤3 条/路/天（通道占用） | ≤2 / ≤1 / ≤1 |
| 漏报率 | 演练注入事件未识别比例 | ≤5% | ≤2% |
| 人脸 1:N 准确率 | 5 万底库首位命中率 | ≥97%（配合活体，误识率 ≤0.1%） | ≥99% |
| 人脸误识率 FAR | 非授权人员被误放行比例 | ≤0.1% | ≤0.01% |
| 活体检测通过率 | 真人通过率 / 照片攻击拦截率 | ≥98% / ≥99% | ≥99.5% / ≥99.9% |
| 推理时延 | 单帧推理耗时 | ≤80 ms（FP16，GPU） | ≤40 ms |
| 端到端时延 | 取帧到事件入库 | ≤500 ms（本地） | ≤300 ms |

**验收方法**

1. 离线评测：在独立测试集（不与训练集重叠）上出具指标报告，含混淆矩阵与 PR 曲线。
2. 现场实测：每类算法选取 5 个代表性点位，连续 72 h 运行，统计误报条数并人工核验。
3. 注入演练：模拟翻越、烟火（安全烟雾发生器）、通道堆物、聚集等场景，验证召回与响应时延。
4. 长稳测试：7×24 h 连续运行 14 天，检查内存、显存、进程存活与事件完整性。
5. 签字确认：算法评测报告与现场验证记录由校方保卫处、信息中心与项目组三方签字。

### 9.1 数据分层设计

```
数据源层：门禁/闸机、摄像机+AI、一卡通、教务/学籍、HR/OA、智能表计、消防主机、访客机、App 埋点
                            │ CDC / MQTT / API / 批量文件
                            ▼

                            │ 清洗、去重、标准化、主数据对齐
                            ▼
DWD 明细层：主题明细宽表（通行明细、事件明细、消费明细、考勤明细、能耗明细），按日分区
                            │ 轻度汇总、维度退化、派生指标
                            ▼
DWS 汇总层：按主题与维度的日/周/月汇总（人员通行画像、宿舍归寝汇总、能耗日汇总、告警统计）
                            │ 指标计算、口径统一
                            ▼
ADS 应用层：面向报表与大屏的指标结果表（在校人数、归寝率、告警闭环率、能耗强度、出勤率）
                            │
                            ▼
应用消费：管理端报表、数据大屏、决策分析、对外数据服务（脱敏）
```

| 层次 | 存储引擎 | 更新频率 | 保留策略 | 典型表 |
| --- | --- | --- | --- | --- |
| ODS | PostgreSQL 分区表 / 对象存储（原始文件） | 实时（CDC）与 T+1 | 30—90 天 | ods_access_raw、ods_ai_event_raw |
| DWD | PostgreSQL 分区表 + 列式压缩 | 准实时（≤5 min）+ T+1 | 2 年（热）/归档（冷） | dwd_access_detail、dwd_event_detail |
| DWS | PostgreSQL 物化视图 / TDengine 降采样 | 小时 + 日 | 5 年 | dws_person_pass_d、dws_energy_d |
| ADS | PostgreSQL 结果表 / Redis 缓存 | 分钟级刷新 | 长期（指标轻量） | ads_kpi_school、ads_dorm_rate |
| 时序 | TDengine | 秒/分钟 | 原始 1 年、降采样 5 年 | energy_metric、env_metric |
| 对象 | MinIO | 实时 | 事件 90 天、人脸原图 30 天（合规） | 事件截图/短视频 |

**核心数据流说明**

1. **准实时链路**：设备事件 → EMQX → 规则引擎 → 业务库（PostgreSQL）→ CDC → DWD/ADS 增量更新（≤5 min），支撑大屏与实时看板。
2. **批处理链路**：每夜 01:00 执行 T+1 全量校准（人员异动、考勤结算、能耗日结），修正准实时链路的偏差。
3. **数据回放**：ODS 保留原始事件，模型或规则调整后可重算 DWD 与 ADS，避免"改口径等于丢历史"。

### 9.3 数据质量与主数据管理

| 管理项 | 规则 | 监控指标 | 处置 |
| --- | --- | --- | --- |
| 唯一性 | 人员唯一以 `person_no` 或 `id_card_hash` 判定；设备唯一以 `device_sn` | 重复率 | 冲突时以权威源（学籍/HR）为准并告警 |
| 完整性 | 必填字段非空率 ≥99%；人脸底库覆盖率（师生）≥98% | 空值率、覆盖率 | 低于阈值通知对应管理员补录 |
| 准确性 | 人脸注册照质量分数 ≥0.7（清晰、正脸、无遮挡）；手机号格式校验 | 注册失败率 | 注册失败引导重拍 |
| 一致性 | 组织路径与人员归属一致；场所层级无环 | 一致性差异条数 | 每日校验任务自动修正 + 报告 |
| 时效性 | 学籍/HR 变更 ≤24 h 同步；设备在线状态 ≤90 s 刷新 | 同步延迟 | 超时告警 |
| 有效性 | 状态值域校验（枚举白名单）；时间字段合理性（如通行时间不得超前 5 min） | 非法值条数 | 拒绝入库并记录 |
| 时效存档 | 临时人员到期自动失效；访客权限到期自动回收 | 过期未停用条数 | 定时任务回收 |

**主数据管理机制**

1. **权威源定义**：学生以学籍/教务系统为权威源，教职工以 HR/OA 为权威源，组织架构以校方人事为准，场所与设备以本平台为准（平台是设备主数据的权威源）。
2. **同步方式**：优先 API/数据库 CDC 增量同步；无接口能力时提供标准 Excel 模板批量导入 + 差异比对。
3. **变更留痕**：主数据变更写入 `md_change_log`，记录变更前后值、操作人、来源系统、时间，支持追溯。
4. **编码规范**：人员编号沿用学号/工号；组织编码继承教务编码并加行政区划前缀；设备编码采用"校区(2)+楼栋(3)+类型(2)+序号(4)"规则，如 `01A01CAM0007`。

### 9.4 数据保留与归档策略

| 数据类型 | 在线保留 | 归档保留 | 归档方式 | 合规依据 |
| --- | --- | --- | --- | --- |
| 通行记录 | 2 年（热） | 5 年 | 分区表转冷存储 + 压缩导出 Parquet | 校园安全管理需要 |
| 车辆通行记录 | 1 年 | 3 年 | 同上 | —— |
| 事件与告警 | 2 年 | 5 年 | 结构化数据归档；截图/视频 90 天后转归档对象存储 | 事件追溯 |
| 视频录像 | 15 天（全量） | 事件片段 90 天 | NVR 循环覆盖 + 事件片段入 MinIO | 分级保留，控成本 |
| 人脸原始图 | 30 天（若业务必需） | 不留存 | 到期自动删除 | 《个人信息保护法》最小必要 |
| 人脸特征向量 | 在职/在读期间 | 离校/离职后 90 天 | 到期删除并留删除日志 | 同上 |
| 消费流水 | 3 年 | 10 年 | 分区转冷 | 财务审计要求 |
| 考勤记录 | 2 年 | 5 年 | 同上 | 人事管理 |
| 能耗数据 | 原始 1 年 | 降采样 5 年（小时/日） | TDengine 多级存储 | 节能分析 |
| 审计日志 | 6 个月（在线） | 3 年 | 归档到不可篡改存储（WORM/哈希链） | 等保 2.0 要求（≥6 个月） |
| 访客登记 | 1 年 | 3 年 | 归档；住宿登记按公安要求 | 公安住宿登记规定 |
| 系统运行日志 | 30 天 | 1 年 | 对象存储 | 运维需要 |

**归档与销毁流程**

1. 定时任务（每月 1 日 02:00）扫描到期数据，生成归档清单并交由数据管理员审核。
2. 审核通过后执行归档：结构化数据导出为 Parquet 并附元数据说明，写入归档区（独立存储桶，只读）。
3. 在线数据按分区 `DROP PARTITION`（比 `DELETE` 高效且不产生大量 WAL）。
4. 到期销毁：人脸原图与特征向量由定时任务删除，同时写入销毁日志（时间、对象类型、数量、执行人、任务 ID），销毁日志不可删除。
5. 每年至少一次归档可恢复性验证（随机抽取 1 个归档包恢复至测试库并校验条数与校验和）。

## 10 接口设计

### 10.1 RESTful API 规范

| 规范项 | 约定 |
| --- | --- |
| 协议 | 生产环境强制 HTTPS（TLS 1.2+，推荐 1.3）；设备侧可用 MQTT over TLS |
| 域名与前缀 | `https://{host}/api/{version}/{module}/{resource}`，如 `/api/v1/access/records` |
| 版本策略 | 主版本入 URL（v1/v2）；同一主版本内只做兼容性增强；弃用提前 6 个月公告并保留双版本 |
| 资源命名 | 名词复数、小写、中划线分隔，如 `dorm-checks`、`visitor-passes` |
| 方法语义 | GET 查询（幂等、安全）、POST 创建/动作、PUT 全量更新、PATCH 局部更新、DELETE 删除（逻辑删除） |
| 查询参数 | `page`（从 1 开始）、`pageSize`（默认 20，最大 200）、`sort=field:asc|desc`、`keyword`、`startTime/endTime`（ISO 8601）、模块特有过滤条件 |
| 时间格式 | ISO 8601 带时区，如 `2026-11-06T08:30:00+08:00`；日期用 `YYYY-MM-DD` |
| 幂等 | 写接口支持 `Idempotency-Key` 请求头；设备事件以 `deviceLocalId` 去重 |
| 分页响应 | `{ items: [], total, page, pageSize }` |
| 限流 | 默认单用户 60 次/分钟，设备 600 次/分钟；超限返回 429 与 `Retry-After` |
| 文件上传 | `multipart/form-data`，单文件 ≤50 MB，返回对象存储 key |
| 长任务 | 返回 `taskId`，通过 `GET /api/v1/tasks/{taskId}` 轮询或 WebSocket 推送进度 |

### 10.3 错误码规范

错误码为 5 位：`A BBCC`，其中 A 为大类，BB 为模块，CC 为具体错误。

### 10.4 鉴权设计

| 场景 | 方案 | 有效期 | 说明 |
| --- | --- | --- | --- |
| 用户登录（Web/移动端） | OAuth2 密码模式或授权码模式，颁发 JWT | Access Token 2 h，Refresh Token 7 天 | JWT 含 userId、tenantId、roles、dataScope、jti |
| 第三方系统对接 | OAuth2 客户端凭证模式（client_credentials） | Access Token 1 h | 颁发 appId/appSecret，绑定 IP 白名单与接口范围 |
| 前端调用 | `Authorization: Bearer <token>` | —— | 网关统一校验签名、过期、黑名单 |
| 设备接入 | 一机一密 + mTLS 双向证书（MQTT） | 证书 3 年，支持吊销（CRL） | 设备证书绑定 deviceId，禁止共用 |
| 设备 HTTP 上报 | HMAC-SHA256 签名 + 时间戳防重放 | 时间窗 ±5 min | 签名串：`method+path+timestamp+nonce+body` |
| 服务间调用 | 内部 mTLS + 短期 JWT（Service Account） | 15 min | 最小权限，按接口授权 |
| 敏感操作二次认证 | 短信验证码或密码二次确认 | 单次有效 | 如导出人脸数据、批量删除、权限变更 |
| 单点登录（可选） | CAS/OIDC 对接校方统一身份 | 会话级 | 减少师生多账号负担 |
| Token 吊销 | Redis 黑名单 + jti 记录 | 至 Token 过期 | 强制下线、密码修改后全量吊销 |

### 10.5 Webhook 事件推送

| 项目 | 约定 |
| --- | --- |
| 触发方式 | 平台向订阅方注册的回调地址 POST JSON |
| 事件类型 | `access.passed`、`vehicle.passed`、`ai.alert`、`dorm.abnormal`、`visitor.arrived`、`attendance.abnormal`、`energy.overrun`、`device.offline`、`device.online`、`workflow.task.created`、`workflow.task.finished` |
| 请求头 | `X-Event-Id`、`X-Event-Type`、`X-Timestamp`、`X-Signature`（HMAC-SHA256，密钥由订阅方持有） |
| 报文结构 | `{ eventId, eventType, eventTime, tenantId, data: {...}, retryCount }` |
| 幂等 | 接收方按 `eventId` 去重；平台对同事件最多推送 3 次（1 min/5 min/30 min 退避） |
| 成功判定 | HTTP 2xx 且响应体 `{"code":0}`；其余视为失败并进入重试队列 |
| 失败处理 | 连续 10 次失败自动暂停订阅并通知管理员；支持手工补推（按时间范围） |
| 安全性 | 仅允许 HTTPS；回调地址注册需管理员审批；支持自定义签名算法（国密 SM3 可选） |
| 订阅管理 | 支持按事件类型、场所范围、级别过滤订阅，避免无效流量 |

### 11.2 网络分区与边界防护

1. **分区原则**：按"服务器区 / 视频专网 / 门禁物联网区 / 办公终端 / 无线网 / 运维管理区 / 出口"七区隔离，跨区默认拒绝。
2. **最小放通**：仅放通业务必需端口（如应用→视频 554/5060/8000，应用→IoT 8883，管理→服务器 22/3389 且仅经堡垒机）。
3. **边界防护**：出口防火墙开启状态检测、IPS、防病毒、应用识别；开启 DDoS 基础防护；禁用高危端口（135/139/445/3389 对外）。
4. **内网东西向**：核心交换机启用端口隔离与 DHCP Snooping/ARP 防护；关键区之间增加微隔离策略。
5. **视频专网**：摄像机禁止访问互联网（ACL 阻断默认网关出站），防止设备被劫持成为跳板。
6. **无线网络**：独立 SSID，访客与师生隔离，启用 WPA3/WPA2-Enterprise；禁用 WPS。
7. **运维通道**：堡垒机统一入口，全程录屏，高危命令二次确认；运维操作留存 ≥6 个月。
8. **暴露面收敛**：仅应用网关与必要回调接口对公网开放，管理后台默认仅内网访问（如需远程，走 VPN + 双因素）。

### 11.3 数据加密与脱敏

| 数据类型 | 存储加密 | 传输加密 | 展示脱敏 | 备注 |
| --- | --- | --- | --- | --- |
| 身份证号 | AES-256-GCM 密文 + SHA-256 哈希（检索用） | TLS | 仅显示后 4 位（如 `****1234`） | 哈希带固定盐值+应用密钥 |
| 手机号 | AES-256-GCM | TLS | `138****5678` | 导出默认脱敏，明文导出需审批 |
| 人脸原始图 | 存储加密（MinIO SSE）+ 私密桶 | TLS | 缩略图加水印（含操作人/时间） | 保留 30 天，到期自动删除 |
| 人脸特征向量 | 向量加密存储（应用层加密后入库） | TLS | 不展示 | 禁止以明文形式导出 |
| 一卡通卡号与余额 | 卡号部分掩码存储；金额不加密（需一致性） | TLS | 卡号 `62******1234` | 交易报文签名防篡改 |
| 视频流 | 本地 NVR 加密卷（可选） | RTSP over TLS / SRTP（可选） | —— | 播放需鉴权与水印 |
| 数据库备份 | AES-256 加密后异地存放 | TLS/SFTP | —— | 备份文件访问需双人授权 |
| 日志与审计 | 敏感字段写入前脱敏 | TLS | 全面脱敏 | 审计日志防篡改（哈希链/WORM） |
| 密钥管理 | KMS/密钥库集中管理，密钥与数据分离，季度轮换 | —— | —— | 密钥绝不硬编码在代码与配置库 |

**脱敏规则生效点**：API 响应序列化层统一处理（基于注解/字段策略），导出文件单独走脱敏模板，日志组件统一过滤器，避免"忘记脱敏"。

### 11.4 人脸等生物特征信息合规

依据《中华人民共和国个人信息保护法》《人脸识别技术应用安全管理办法》及《信息安全技术 个人信息安全规范》，落实以下要求：

| 合规要求 | 落地措施 |
| --- | --- |
| 单独同意 | 人脸采集前通过 App/纸质+电子方式取得**单独同意**，不与一揽子条款捆绑；同意记录（时间、版本、方式、IP）留存可查 |
| 告知义务 | 告知处理目的（门禁通行/考勤/安全防范）、方式、范围、保存期限、拒绝后果、投诉渠道 |
| 替代方式 | 必须提供**非人脸替代通行方式**（刷卡/二维码），不得因拒绝刷脸而限制正常出入校园 |
| 最小必要 | 仅采集门禁、考勤、安防必需的点位；宿舍、卫生间、更衣室等私密空间**严禁安装**人脸识别设备 |
| 比例原则 | 仅在"维护公共安全所必需"场景使用；不得用于分析学生行为画像、情绪识别、消费能力评估等无关用途 |
| 本地化处理 | 人脸特征优先在边缘/本地比对，原始图中转不落地；确需上云的仅上传特征向量（加密） |
| 存储限制 | 原始人脸图默认不留存（或 ≤30 天）；特征向量在校期间留存，离校/离职 90 天内删除并留删除日志 |
| 访问控制 | 人脸数据访问需专门权限 + 双人授权 + 全程审计；批量导出禁止（如需，走审批 + 水印 + 只读） |
| 安全防护 | 加密存储、脱敏展示、防批量爬取（限流 + 异常检测）、防内部越权 |
| 未成年人保护 | 未满 14 周岁学生的人脸信息取得监护人同意，作为敏感个人信息处理并单独记录 |
| 第三方约束 | 若使用第三方算法/云服务，须签数据处理协议，明确不得留存、不得二次利用 |
| 影响评估 | 上线前完成个人信息保护影响评估（PIA）并留存报告，重大变更重新评估 |
| 权利响应 | 提供查询、更正、删除、撤回同意的线上入口，受理 ≤15 个工作日闭环 |
| 违规追责 | 建立数据操作责任到人机制，违规操作审计留痕并追责 |

### 11.5 访问控制模型

采用 **RBAC + 数据权限 + 属性条件** 的复合模型：

| 层次 | 模型 | 说明 | 示例 |
| --- | --- | --- | --- |
| 功能权限 | RBAC | 用户—角色—权限（菜单/按钮/API）三级绑定 | 宿管员拥有"查寝"菜单与"提交查寝结果"按钮 |
| 数据权限 | 数据范围（5 类） | 全部 / 本校区 / 本部门及下级 / 本部门 / 本人及所管 | 班主任仅见本班学生通行记录 |
| 字段权限 | 字段级掩码 | 敏感字段按角色决定是否脱敏 | 保卫处可见手机号，普通教师不可见 |
| 属性条件 | ABAC（规则） | 基于时间、地点、设备、级别的动态判定 | 仅工作日 22:00—06:00 允许查看 AI 告警详情 |
| 岗位代理 | 委托授权 | 请假/出差期间权限临时委托，到期自动回收 | 学工主任出差期间委托副主任审批 |
| 最小权限 | 默认拒绝 | 新增角色默认无权限，按需授予 | —— |
| 职责分离 | SoD | 审批人不得同时是申请人；审计员不得有业务写权限 | —— |

**权限变更流程**：申请 → 部门负责人审批 → 安全管理员复核 → 生效 → 记录留痕；关键权限（人脸导出、全量数据导出、日志删除）需双人审批。权限每季度复核一次，离岗/转岗即时回收。

### 11.6 审计日志

| 审计对象 | 记录内容 | 保留期 | 存储 |
| --- | --- | --- | --- |
| 用户登录 | 账号、IP、设备指纹、结果、失败原因 | 3 年 | 日志平台（不可篡改） |
| 敏感数据访问 | 谁、何时、访问了哪些人员/照片、目的 | 3 年 | 同上 |

### 11.7 容灾备份与 RPO/RTO

| 对象 | 备份策略 | RPO | RTO | 验证频率 |
| --- | --- | --- | --- | --- |
| PostgreSQL（业务库） | 主备流复制（同步/准同步）+ 每日全备 + WAL 归档 | ≤1 min（主备）/ ≤5 min（异地） | ≤30 min | 每季度恢复演练 |
| TDengine（时序库） | 每日全备 + 副本（商业版 2 副本） | ≤1 h | ≤2 h | 每半年 |
| Redis | AOF everysec + 每日 RDB | ≤1 s | ≤10 min | 每季度 |
| MinIO（对象） | 纠删码 + 跨节点复制；关键桶异地备份 | ≤15 min | ≤1 h | 每季度 |
| 配置与代码 | Git 仓库 + 配置中心版本化 + 每日导出 | ≈0 | ≤30 min | 每次变更 |
| 边缘节点配置（白名单/规则） | 平台版本化保存 + 边缘本地副本 | ≤5 min | ≤30 min | 每月 |
| 整机房灾难 | 异地备份 + 分校区降级运行 + 云上冷备 | ≤4 h | ≤8 h | 每半年演练 |

**容灾分级**

- **一级（本地高可用）**：单机房内主备/集群，硬件故障不影响业务。
- **二级（同城异地）**：备份数据置于不同楼栋/不同校区，防火灾水淹。
- **三级（异地/云备）**：关键数据（主数据、权限、审计）加密后同步至云对象存储，作为最后防线。

**演练要求**：每半年至少一次完整演练，覆盖数据库切换、门禁离线自治、边缘事件补传、备份恢复四项，形成演练报告并跟踪整改。

### 12.3 降级与离线续传方案

| 故障场景 | 降级策略 | 用户体验 | 恢复动作 |
| --- | --- | --- | --- |
| 平台不可用（中心故障） | 门禁/道闸按边缘本地白名单与规则独立运行；人脸比对在边缘完成 | 通行不受影响，仅无实时记录上云 | 平台恢复后边缘按序补传事件（含时间戳） |
| 边缘与中心断网 | 事件本地缓存（≥72 h，磁盘水位 <85%），平台侧规则失效则用边缘兜底规则 | 通行、告警本地照常 | 网络恢复 5 min 内补传，平台按时间戳排序入库并重新计算考勤/归寝 |
| 边缘 GPU 故障 | 降级为 RTSP 直存 + 移动侦测告警；或切换备用边缘节点 | 智能分析能力下降，视频不中断 | 抢修后回溯录像补算（对关键时段） |
| 数据库主库故障 | 只读模式运行（查询可用，写入队列缓存）；门禁不受影响 | 无法新增/修改，查询正常 | 主备切换后消费队列补写 |
| Redis 故障 | 本地内存缓存兜底，会话改为短时 JWT 自校验 | 登录态可能需重新登录 | 恢复后重建缓存 |
| 消息队列故障 | 边缘继续本地缓存；应用侧写入重试队列（指数退避） | 时延增大但数据不丢 | 恢复后批量补投 |
| 视频平台故障 | 边缘直连摄像机（RTSP），NVR 继续录像 | 实时预览受限，录像完整 | 恢复后同步通道 |
| 存储满 | 按策略清理最旧归档数据；事件只保留结构化数据 + 缩略图 | 无感知 | 扩容或调整保留策略并告警 |
| AI 误报风暴 | 触发风暴抑制，自动降级为"仅记录不派单" | 值班压力不增加 | 人工确认后恢复派单 |
| 断网时考勤/归寝计算 | 边缘缓存原始通行记录；平台恢复后按原始时间戳重算 | 报表延迟，数据准确 | 自动重算并覆盖中间结果 |

**离线续传技术要点**

1. 边缘侧使用本地 SQLite/时序文件存储事件，写入带本地自增序号与 UTC 时间戳。
2. 上报采用 MQTT QoS1（至少一次）→ 平台按 `(deviceId, deviceLocalId)` 唯一键幂等去重。
3. 补传采用批量 + 限速（默认 200 条/秒），避免平台恢复瞬间被冲击；支持断点续传（记录已确认的最大序号）。
4. 平台侧对补传数据触发的派生业务（考勤、归寝、告警统计）具备**重算开关**，避免离线期间产生错误的"缺卡/未归"告警。
5. 离线期间产生的通行记录标注 `offline=true`，在报表中可识别，便于解释数据波动。

### 13.2 规则引擎设计要点

规则以"**事件 + 条件 + 动作**"三元组表达，支持可视化配置与热更新：

```
规则示例：学生请假放行
WHEN  leave.approved (event)
IF    leave.type IN (事假, 病假) AND leave.duration_hours <= 72
THEN  action: grantTempAccess(personId, gates=[校门], validFrom=leave.start, validTo=leave.end)
      action: notify(targets=[班主任, 宿管], template="leave_granted")
      action: syncDormExpect(personId, status=请假)
ELSE  action: notify(targets=[学工主任], template="leave_need_review")
```

| 能力 | 说明 |
| --- | --- |
| 条件表达式 | 支持字段比较、集合包含、时间窗、地理围栏、正则匹配，组合 AND/OR/NOT |
| 动作类型 | 下发授权、下发指令、生成工单、发通知、写标签、调用 HTTP、写数据表、触发工作流 |
| 优先级与互斥 | 规则按优先级顺序匹配，支持"命中即停"或"全部执行" |
| 灰度与模拟 | 新规则可先在"影子模式"运行，只记录不执行，验证命中量 |
| 版本与回滚 | 规则版本化，一键回滚；变更需审批并留痕 |
| 限流保护 | 单位时间动作次数上限，防规则写错导致指令风暴 |
| 测试 | 内置测试用例集（给定事件，期望动作），发布前必须通过 |

### 15.4 结语

本方案以"**边缘智能 + 软件平台 + 标准协议**"为主线，在有限硬件预算下实现 12 个一级模块的一体化覆盖：以端—边—云六层架构承载感知与计算，以统一 IoT 物模型与规则引擎承载跨模块联动，以 PostgreSQL + TDengine + MinIO 的数据底座承载主数据与分析，以等保三级与个人信息合规要求约束安全边界，以竞赛版/商业版双轨选型兼顾"比赛能演示、学校能落地、产品能复制"。本文件作为开发与实施的技术基线，后续变更须经架构评审并更新修订记录。
